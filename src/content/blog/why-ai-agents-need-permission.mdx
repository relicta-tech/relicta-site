AI coding tools can create a pull request, revise a migration, or prepare a release summary in minutes. Those capabilities do not answer the questions a release owner still has to answer:

- What is included in this release?
- Which version should it receive?
- What risk and policy signals apply?
- Does it need a human decision before publishing?
- What should customers be told?

Those are release-decision questions. They matter whether the change was written by a person, an agent, or both.

## Approval in one workflow is not control over every action

An AI agent may have credentials for source control, cloud services, issue trackers, or deployment tools. A release-governance tool cannot stop the agent from using credentials outside the workflow it manages.

Relicta focuses on the release operations routed through Relicta: analyzing repository changes, recommending a version, evaluating configured governance policy, recording approval, and running configured publishing steps. Use repository permissions, CI checks, and deployment controls to govern other actions.

This boundary is deliberate. It makes the decision Relicta records understandable: a particular release plan was evaluated under a particular configuration, then approved or rejected by an identified actor.

## Give reviewers a useful release packet

Release review is easier when reviewers can examine the same information together:

1. The commits and files included in the plan.
2. The proposed version and structured change summary.
3. Risk signals and configured policy results.
4. The release notes and required approvals.
5. The resulting decision record.

Relicta's CLI and MCP server expose release planning and governance steps to people and compatible coding agents. The configured policy determines whether an action can proceed or needs approval. A recorded decision does not certify that the software is correct; reviewers still need the normal engineering evidence.

## Keep customer communication tied to the changes

Technical commit messages often need translation before they can be shared with customers. Start the writing process from a release recommendation and its structured change summary, then add product context and review every claim.

In the public v4.2.0 release, Relicta can produce deterministic notes or use a configured AI provider. The unreleased v5 source also supports saving customer-facing notes written in an MCP-connected agent session. That workflow lets an agent use product context from its conversation while keeping the supplied draft attached to the release for human review. Relicta does not fact-check generated or agent-authored prose.

## Keep the audit record in perspective

Relicta can preserve governance decisions in a hash-chained record and verify the chain with `relicta audit verify`. That record helps explain what the release workflow decided and why. It does not capture every action taken by an agent, prove that a policy is adequate, or establish regulatory compliance on its own.

Use it alongside the controls your team already relies on: narrow credentials, protected branches, CI checks, deployment approvals, and incident processes. The goal is a clearer release decision and a usable record of that decision—not a claim that one tool governs an entire engineering organization.

## Start with a dry run

Try Relicta on a repository and inspect a plan before connecting it to publishing credentials:

```bash
relicta plan --dry-run
```

Check that the proposed changes, version, and policy signals match your expectations. Then configure approval and publishing steps for the workflow you want Relicta to manage.
