Release automation can create a tag and upload an artifact. A release owner still needs to understand what changed, what context informed the decision, and which checks or approvals happened before publication.

Relicta v4.2.0, published in July 2026, adds more context to that release-time decision and improves how Relicta works with plugins and MCP clients. It is a focused update to the release workflow, not a general-purpose control plane for every action an AI agent takes.

## More context for release decisions

Relicta can include verifiable contribution history and organization-granted identities when evaluating whether an actor may approve a change. Governance decisions can also include commit authorship and available agent-memory context.

That context helps a configured policy make a more informed release decision. It does not prove that a change is correct or safe, and it does not replace code review, repository permissions, or CI checks. Teams remain responsible for deciding which evidence and policy rules are appropriate for their repositories.

## Safer plugin execution on macOS

Relicta v4.2.0 applies operating-system sandbox restrictions to macOS plugins. Plugin isolation still depends on the platform and the restrictions the plugin declares; review the plugin's trust and sandbox details before enabling it.

Relicta's plugin boundary applies to plugin processes launched by Relicta. It does not constrain other tools or actions performed directly by an AI agent, developer, or CI runner.

## Structured responses for MCP clients

The MCP server publishes output schemas for its data tools. MCP clients can use those schemas to interpret responses more consistently when they plan or review a release.

An agent can ask Relicta for a release recommendation and use the returned change summary as source material. In the current public v4.2.0 release, customer-facing prose still comes from deterministic templates or a configured AI provider. Saving notes composed with product context from the agent's conversation is part of the unreleased v5 source workflow, not a v4.2.0 capability.

## The boundary Relicta covers

Relicta governs release operations that teams route through its configured workflow: planning, policy evaluation, approval, and configured publishing steps. An agent with separate credentials can still call other services directly. Keep those permissions narrow and use source-control protections, CI checks, and deployment controls alongside Relicta.

The audit trail records release decisions and can be checked with `relicta audit verify`. It is tamper-evident evidence about the recorded workflow; it is not a guarantee that all organizational or production actions were routed through Relicta.

## Try the published release

Relicta v4.2.0 is open source. Review the [installation guidance](https://docs.relicta.tech/install), [release notes](https://github.com/relicta-tech/relicta/releases/tag/v4.2.0), and the documented platform and security limits before adopting it.

```bash
relicta init
relicta plan
```

The plan is a reviewable recommendation. Approval and publication remain separate steps governed by your configuration.
